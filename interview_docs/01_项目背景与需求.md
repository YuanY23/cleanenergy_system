# 01 项目背景与需求

> 证据基线：本章量化内容均对应 `run_id=formal-2024-20260809T131238Z`。业务来源以仓库文档、公开来源登记和正式输入为准；无法证明的真实企业背景统一标记 `【需要项目作者补充】`。

## 1. 项目解决的不是单一“调度题”

园区同时存在三条需求链：

- 电：常规生产和辅助系统用电，年需求 3.10 TWh，峰值 450 MW；
- 热：工艺或采暖等热需求，年需求 1.15 TWhth，峰值 270 MWth；
- 氢：连续工业用氢任务，30 t/d、10,980 t/y。

供给侧包含风电、光伏、电网、天然气锅炉；转换和储能侧包含热泵、电解槽、储氢罐、燃料电池和电池。电解槽把电转成氢，燃料电池把氢转回电，热泵把电转成热，因此任何容量或调度决策都会在多能流之间传导。

仓库没有给出具体企业名称、建设地点的可公开坐标、真实产线类型、业主投资预算、并网批复和设备厂商报价。因此这些内容不能在面试中自行补齐：`【需要项目作者补充】`。

## 2. 需求拆解

### 2.1 业务需求

1. 在正常并网年份满足电、热、氢需求。
2. 比较三种决策偏好，而不是只输出一个“最佳方案”：
   - 经济型：最小化年化总成本；
   - 低碳型：在经济型成本的 110% 上限内最小化运行碳排；
   - 韧性型：加入关键负荷功率和电池时长的工程对标约束后最小化成本。
3. 输出可解释的容量、运行、碳排、可靠性与敏感性结果。
4. 对停电和关键设备故障做压力测试，但不冒充概率可靠性认证。

对应入口是 [`run_formal_study()`](../src/zero_carbon_park/formal_study.py)，三方案在 [`solve_engineering_portfolios()`](../src/zero_carbon_park/planning/runner.py) 中分别构建和求解。

### 2.2 数据需求

- 统一采用 2024 年闰年 8,784 小时时轴；本地时区必须连续、无重复、无缺口。
- 生产气象必须来自 ERA5；NASA POWER 只能独立交叉核验，不能在缺数时偷偷替换 ERA5。
- 负荷必须同时满足公开尺度的年总量和峰值约束，并明确标为合成数据。
- 每项关键参数需要来源或假设登记，输入文件需要 SHA-256 哈希。

数据入口集中在 [`annual_pipeline.py`](../src/zero_carbon_park/data/annual_pipeline.py)、[`generator.py`](../src/zero_carbon_park/data/generator.py)、[`sources.py`](../src/zero_carbon_park/data/sources.py) 和 [`config.py`](../src/zero_carbon_park/config.py)。

### 2.3 建模需求

模型要回答两层不同问题：

- **规划层**：“该装多少？”——风、光、电池功率/能量、电解槽、储氢、燃料电池、热泵是容量变量。
- **运行层**：“每小时怎么调？”——购电、弃风弃光、充放电、制氢、储氢、燃料电池、热泵和锅炉出力是调度变量。

对应代码：[`planning/variables.py`](../src/zero_carbon_park/planning/variables.py) 建变量，[`planning/constraints.py`](../src/zero_carbon_park/planning/constraints.py) 建物理和工程约束，[`planning/objective.py`](../src/zero_carbon_park/planning/objective.py) 建目标函数。

### 2.4 验证需求

代表日规划的结果不能直接当作全年运行结论，因此正式流程要求：

1. 检查代表日年度和月度重构误差；
2. 固定容量做完整 8,784 小时滚动回放；
3. 检查小时覆盖、时间轴、电平衡残差和正常年 ENS；
4. 从回放真实状态发起确定性孤网事件；
5. 将所有结果追溯到清单中的原始 CSV。

## 3. 非功能需求

### 可复现

[`build_run_manifest()`](../src/zero_carbon_park/config.py) 创建不可变运行目录，记录输入哈希、Git 提交、排除的历史路径和运行 ID。正式入口只接受清单声明的输入，不扫描“名字相似”的工作簿。

### 可审计

正式输出拆分为 `inputs/`、`representative_periods/`、`planning/`、`replay/`、`reliability/`、`metrics/` 和 `reporting/`。图表函数只使用调用者提供的数据，不在绘图阶段重新计算 KPI，见 [`reporting/plots.py`](../src/zero_carbon_park/reporting/plots.py)。

### 安全

气象下载在写文件前检查凭据；API 密钥、账号、本机路径凭据不得写入仓库。该规则体现在 [`annual_pipeline.py`](../src/zero_carbon_park/data/annual_pipeline.py) 和项目 `AGENTS.md`。

### 结果纪律

- 低碳型终止于时间上限，实际 MIP gap 1.3349%，只能说“时限内可行解”。
- 54 个事件是确定性设计事件，不能改写成 EENS、LOLP、SAIDI、SAIFI。
- 外送电限制为 0，正式结果也没有售电；即便未来允许售电，当前碳核算公式也不会自动用外送电抵扣运行排放。
- 120% 和 4 h 是工程对标，不是法规或认证门槛。

| 低碳成本预算 | 年化成本上限 | `add_capacity_planning_objective()` 创建 `annual_total_cost_cap_constraint` | 低碳型年成本恰为经济型 110%，余量为 0 |
| 韧性装机 | firm power 与 4 h 能量约束 | `add_planning_constraints()` 创建两项 secure 约束 | 162 MW、648 MWh，约束余量均为 0 |
| 求解可接受 | 状态、incumbent、实际 gap | `optimization/solver.py` | 经济/韧性 optimal；低碳 time limit 有可行 incumbent |
| 可追溯 | 清单、哈希、完成标志、原始 CSV | `config.py`、`formal_study.py` | `manifest.json`、`completion.json`、`artifacts/latest.json` |
