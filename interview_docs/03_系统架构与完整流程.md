# 03 系统架构与完整流程

> 本章所有正式数字对应 `run_id=formal-2024-20260809T131238Z`。架构以 `run_formal_study()` 的真实调用链为主；CLI 中的旧 S0—S5、旧典型日、随机/鲁棒规划入口只作为历史兼容代码。

## 1. 分层架构

```text
外部公开数据/工程假设
        │
        ▼
数据治理层：来源登记、凭据前检、哈希、时区与完整性
        │
        ▼
输入构造层：ERA5→风光CF；公开尺度→电/热/氢合成负荷；电价/碳因子
        │
        ├──────────────► NASA POWER 月度独立交叉核验
        ▼
代表期层：日特征标准化→强制极端日→k-medoids→误差门槛→k=12
        │
        ▼
规划层：经济型 / 低碳型 / 韧性型容量规划 MILP
        │ 固定容量
        ▼
全年回放层：336h 前视、168h 提交，53 个窗口拼成 8784h
        │ 从真实状态抽取起点
        ▼
可靠性层：18 个确定性孤网/设备故障事件 × 3 个方案
        │
        ▼
指标与报告层：成本、容量、碳排、ENS、敏感性、图表、完成标志
```

## 2. 正式入口与生命周期

正式入口是 [`scripts/run_formal_study.py`](../scripts/run_formal_study.py)，它只解析清单路径并调用 [`run_formal_study()`](../src/zero_carbon_park/formal_study.py)。完整生命周期如下：

1. `load_verified_manifest()` 验证 run_id、输入路径、哈希、Git 提交和历史排除边界。
2. 读取/生成 8,784 小时生产输入和气象质量证据。
3. 对 k=8、12、16 构建代表日，导出映射、权重、转移计数和误差诊断。
4. 按门槛选 k=12。
5. `solve_engineering_portfolios()` 分别求经济、低碳、韧性容量。
6. `run_rolling_replay()` 固定各自容量做全年滚动回放。
7. `_canonical_reliability_starts()` 从回放中找四种状态压力起点。
8. `_reliability_events()` 生成 18 个事件；`run_reliability_catalog()` 对每个方案求解。
9. 聚合成本、碳排、可靠性和固定解敏感性；导出 CSV、图和技术报告。
10. 全部检查通过后写 `completion.json`，再原子更新 `artifacts/latest.json`。

## 3. 数据流与对象流

### 3.1 输入侧

- `AnnualWeatherConfig`：位置、年份、光伏/风机物理参数。
- `LoadReconstructionConfig`：年总量、峰值和负荷形状参数。
- `StudyConfig`：容量上界、求解器、可靠性和工程约束。
- `SourceRegistry`：来源、适用字段、时间范围、哈希和“是否测量值”边界。

主要文件：[`config.py`](../src/zero_carbon_park/config.py)、[`data/annual_pipeline.py`](../src/zero_carbon_park/data/annual_pipeline.py)、[`data/sources.py`](../src/zero_carbon_park/data/sources.py)。

### 3.2 代表日侧

输入 366 个自然日，每个日向量包含电负荷、热负荷、氢负荷、PV CF、风 CF 和价格等 24 小时形状。输出：

- `representative_days.csv`：12 个实际日期和权重；
- `representative_hourly.csv`：12×24 小时规划输入；
- `day_mapping.csv`：全年每一天映射到哪个代表日；
- `transition_counts.csv`、`chronology_links.csv`：原始日序列中的转移统计；
- `compression_diagnostics.csv`：年度/月度能量和形状误差。

关键边界：当前 [`planning/builder.py`](../src/zero_carbon_park/planning/builder.py) 没有读取 `transition_counts` 或 `chronology_links`。规划模型对每个代表日使用各自的状态边界；跨日连续性由后续全年回放检验。不能声称当前规划层已经实现基于转移矩阵的季节储能链接。

### 3.3 规划侧

`build_capacity_planning_model()` 接收代表日逐时表、设备参数、成本参数和方案配置，依次执行：

1. `add_capacity_variables()`：八类容量；
2. 逐时调度变量：购售电、风光利用/弃电、分级失供、充放电、SOC、制氢、储氢、燃料电池、热泵、锅炉；
3. `add_*_constraints()`：资源上限、多能平衡、设备状态、工程约束；
4. `add_capacity_planning_objective()`：创建代表日权重年化运行成本、容量年化投资、成本上限和目标；
5. `add_capacity_planning_objective()`：根据方案选择成本或碳目标。

求解由 [`optimization/solver.py`](../src/zero_carbon_park/optimization/solver.py) 调用 `appsi_highs`，并把终止条件、incumbent、上/下界和实际 gap 显式带回。

### 3.4 回放侧

容量从 `planning_capacity.csv` 读取并固定，不在回放中重新投资。滚动窗口：

- 前视长度 336 h；
- 每次只提交前 168 h；
- 53 个窗口覆盖全年；
- 最后一个窗口只剩 48 h；
- 状态从已提交窗口的末值传到下一窗；
- 最终窗口施加年度状态闭合目标/边界。

这是一种“模型预测控制式”的离线回放，但每个窗口使用已知的未来输入，不包含预测误差，不能直接称实时 MPC 控制器。

### 3.5 可靠性侧

事件开始状态不是统一假设的“满电满氢”，而是取自全年回放的事件前状态：

- 最低电池 SOC；
- 最低储氢量；
- 最低可再生可用功率；
- 每月高负荷候选中的全局高电负荷。

四个起点分别配 2/4/8/24 h 停电，另在最低可再生起点增加电池故障 24 h、燃料电池故障 24 h，共 18 个事件/方案。事件调度允许电负荷和氢负荷以高惩罚松弛，否则极端事件可能不可解。

## 4. 三个方案的分叉点

| 层面 | 经济型 | 低碳型 | 韧性型 |
|---|---|---|---|
| 目标 | 最小年化总成本 | 成本≤经济型 110% 时最小运行碳排 | 加工程韧性约束后最小年化总成本 |
| 正常年失供 | 固定为 0 | 固定为 0 | 模型保留分级失供，但结果为 0；另有关键供给率约束 |
| 外购氢 | 允许，高成本 | 允许，高成本 | 禁止 |
| 规划是否孤网 | 否 | 否 | 否；正式配置 `resilience_planning_islanded=False` |
| firm power | 无 | 无 | 电池功率+燃料电池≥120% 峰值关键负荷 |
| 电池时长 | 无 | 无 | 电池能量≥4×电池功率 |
| 事件验证 | 18 个 | 18 个 | 18 个 |

## 6. 失败模式与保护

- 输入哈希不一致、清单引用仓库外文件、Git 提交不匹配：清单验证失败。
- ERA5 缺小时、重复小时、时区错误：气象质量检查失败。
- 求解无 incumbent：不导出“伪答案”。
- 超时但有 incumbent：保留可行解，并记录 time limit 和 actual gap。
- 回放小时重复/缺失、平衡残差超限：不标记 `passed`。
- 正式模式请求旧分析 action：[`cli.py`](../src/zero_carbon_park/cli.py) 主动拒绝。
- 完成前不会更新 `latest.json`，避免半套结果成为当前基线。

## 7. 面试追问抓手

如果面试官问“为什么不一步到位做全年联合规划”，从三个层次回答：

1. 计算：容量+8,784 小时+二进制互斥会显著放大 MILP。
2. 方法：代表日用于找到装机，全年回放用于检验运行，事件用于检验极端状态，各层问题不同。
3. 诚实边界：这种分解牺牲了“全年时序与容量一次性联合最优”；特别是季节储能可能被代表日边界弱化，因此必须靠全年回放暴露偏差，未来可做带状态链接的代表期或分解算法。
